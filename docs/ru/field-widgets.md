# Проект расширения виджетов полей

**Только варианты дизайна; новый API виджетов не реализован.** Уже существуют
`FieldOptions.template`, `parser` и `formatter` для собственного рендеринга и преобразования
значений. См. [расширения](extensions.md). Ниже — варианты будущего единого механизма
переиспользуемых виджетов для SQL reflection и ORM-адаптеров.

| Подход | Плюсы | Минусы и риски |
|---|---|---|
| Расширить template overrides декларацией локальных CSS/JS | Минимальные изменения; текущий контекст Jinja; удобно для одного приложения | Валидация и ассеты настраиваются отдельно; повторяется код доступности и инициализации; нужен стабильный контракт контекста |
| Именованный реестр и имя/параметры виджета у поля | Переиспользование, явный allowlist, дедупликация ассетов, defaults по метаданным | Нужны публичный контекст, схема конфигурации, lifecycle и правила совместимости; приоритет defaults становится частью API |
| Python-класс/протокол Widget с render/parse/assets | Рендеринг и преобразование рядом; удобные серверные тесты и составные контролы | Больше публичного Python API; риск связать бизнес-парсинг с UI; нужны правила async и нескольких input |
| Frontend-плагины или web components | Подходит для редакторов, карт и сложных контролов; можно использовать frontend-библиотеки | Больше JS и сборки, сопровождение CSP/зависимостей; нужны гидрация, no-script fallback и доступность |

## Предпочтительный вариант

Начать с **именованного реестра**, где первая реализация виджета основана на шаблоне.
Python-протокол можно добавить позднее, если он понадобится составным полям.
Выбор виджета должен быть независим от адаптера: `Field` описывает данные, настройки
поля коллекции выбирают отображение. Встроенные defaults определяются kind и необязательными
метаданными вроде multiline/max length; явный выбор для поля имеет приоритет.

Концептуальная регистрация связывает имя с шаблоном, проверяемыми параметрами и манифестом
локальных ассетов. Это описание дизайна, не рабочий API. Поле получает стабильный контекст:
метаданные, значение, name/id, подпись, ID подсказок/ошибок, nullable/default и read-only.
Ассеты загружаются один раз только на нужных страницах и добавляют точные хеши в CSP.
Произвольные remote-ассеты и исполняемый inline-конфиг не должны обходить текущую политику.

Первая версия должна отправлять одно каноническое значение на поле через существующие
parser/formatter. Виджет с несколькими контролами собирает их значения в один input;
бизнес-изменения нескольких полей остаются операциями приложения/сервиса, пока отдельно
не определён атомарный контракт разбора. Виджет не даёт права записи, не раскрывает скрытые
значения и не отменяет CSRF/revision или серверную валидацию.

Нужны клавиатура и screen reader, перевод сообщений, экранирование, сохранение введённого
после 422/409, явный no-script fallback, teardown инициализации и дедупликация ассетов.
Интеграционные тесты примера должны работать в FastAPI и Litestar, с SQL reflection и ORM,
проверять read-only/скрытые поля, точность чисел и часовые пояса.

Контекст шаблона следует версионировать отдельно от обязательного adapter API version 1.
Добавление реестра не требует bump API адаптера; изменение обязательных метаданных — требует.
Новый API расширения стоит выпускать после определения контекста и lifecycle ассетов.
