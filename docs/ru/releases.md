# Релизы и политика совместимости

История выпусков и инструкции перехода находятся в [CHANGELOG](https://github.com/lyova24/quite-admin/blob/master/CHANGELOG.md). Обновление версии не создаёт тег или релиз.

## Правила версий

- PATCH: совместимые исправления ошибок, безопасности и runtime-зависимостей.
- MINOR: новые возможности; до 1.0 также явно описанные несовместимые изменения.
- MAJOR после 1.0: изменение обязательного API, удаление функций или runtime-поддержки.

Для пакета изменений выбирается один максимальный bump. `pyproject.toml`, публичный
`__version__`, `uv.lock`, README, UI и документация меняются вместе. До первого
опубликованного релиза точка отсчёта — предыдущая записанная версия. Каждая задача
имеет отдельный Conventional Commit. Коммит сам по себе пакет не публикует.
Изменение обязательного контракта адаптера также поднимает `ADAPTER_API_VERSION`.

Библиотека следует явным [гарантиям публичного API](api-stability.md). До 1.0
несовместимость требует MINOR и миграции EN/RU, после 1.0 — MAJOR. Deprecated API
сохраняется хотя бы ещё один совместимый MINOR-релиз с объявлением замены и версии
удаления. Поддержка Python/framework/ORM определяется проверенной матрицей, а не только
диапазонами зависимостей.

## Выпуск

1. Зафиксировать версию, дату changelog и миграцию.
2. Отправить коммит в `master` и дождаться `ci.yml`. Автоматический запуск выбирает
   проверки по изменённым файлам. Перед тегом нужен успешный **Release ready**: если он
   пропущен, выполнить **Actions → ci → Run workflow → master** (или
   `gh workflow run ci.yml --ref master`) и дождаться полного прогона на этом точном коммите.
3. Запустить `python scripts/check_release.py --tag v<project.version>`.
4. После разрешения отправить тег. `release.yml` требует успешный полный CI из `master`
   и его артефакт документации для точного коммита тега, затем публикует GitHub release
   с changelog этой версии и помечает его Latest.
5. После успешного workflow `pages.yml` выкладывает готовый артефакт документации из CI.
   Параллельно `pypi.yml` собирает **один универсальный wheel и один sdist** на Python 3.12,
   проверяет Twine и устанавливает каждый в чистое окружение.
6. Отдельная job загружает проверенные файлы в PyPI через Trusted Publishing.
   Последняя job устанавливает точную версию из публичного индекса и проверяет ресурсы.

Релиз не перезапускает матрицу тестов. Последний запуск `ci.yml` для SHA тега от пуша
в `master` или ручного запуска на `master` должен завершиться успешно, включая
**CI ready** и **Release ready**. Сокращённый зелёный прогон позволяет merge, но не
разрешает публикацию. Старый зелёный результат не скрывает новый упавший, отменённый,
незавершённый или сокращённый запуск. CI из PR и других веток не разрешает релиз.
Полный прогон нужно выполнить до создания тега, пока `master` указывает на коммит релиза;
любой следующий коммит требует собственной проверки.

Отсутствующий или просроченный артефакт документации также блокирует релиз; пересоберите
его перезапуском полного CI. Pages публикует версию тега, даже если `master` уже
продвинулся, используя артефакт документации из того же полного прогона без повторной
сборки и тестов демо. Автоматическая и ручная загрузка в PyPI проверяют тот же полный
CI, но повторно не требуют артефакт документации.

Создание релиза через интерфейс GitHub проверяет тот же готовый результат CI перед
публикацией Pages и PyPI. Пакет собирается из проверенного коммита по SHA; автоматическая
и ручная публикация повторно проверяют статус CI из `master` и соответствие опубликованного
тега этому коммиту.

В GitHub release остаются автоматические архивы исходников ZIP/tar.gz. Wheel/sdist
публикуются в PyPI, не в assets GitHub. Python-матрица не собирает пакеты. Оба дистрибутива
явно используют metadata **2.4**; проверка отклоняет другую версию метаданных.

## Одноразовая настройка PyPI

Войдите в PyPI и добавьте pending publisher в
[настройках публикации аккаунта](https://pypi.org/manage/account/publishing/) для первой
загрузки либо настройте издателя на странице Publishing существующего проекта:

| Поле | Значение |
|---|---|
| Проект PyPI | `quite-admin` |
| Владелец GitHub | `lyova24` |
| Репозиторий | `quite-admin` |
| Имя workflow | `pypi.yml` |
| Окружение GitHub | `pypi` |

Job загрузки использует GitHub environment `pypi`. Только у неё есть `id-token: write`;
в ней нет checkout и выполнения кода проекта. PyPI обменивает OIDC identity GitHub на
короткоживущие права загрузки. Постоянный PyPI-токен не нужен ни в secrets, ни в репозитории.
При необходимости настройте reviewers окружения для ручного разрешения публикации.
См. [официальную настройку PyPI](https://docs.pypi.org/trusted-publishers/adding-a-publisher/).

PyPI workflow самостоятельный, не reusable: издатель всегда сопоставляется с `pypi.yml`.
Он принимает только успешные release-запуски этого репозитория и проверяет, что тег
по-прежнему указывает на проверенный коммит, а GitHub release опубликован.
Для повтора запустите **publish to PyPI** вручную из `master`, указав существующий тег,
`v<project.version>`. Ручной запуск проверяет тот же последний CI из `master` для коммита
пакета, но не требует повторного наличия артефакта документации. Уже загруженные файлы
пропускаются при повторе; версии PyPI нельзя перезаписать.
Не перемещайте опубликованный тег для изменения загруженного пакета.

## Установка пакетным менеджером

```bash
pip install 'quite-admin[sqlalchemy,fastapi]'
uv add 'quite-admin[sqlalchemy,litestar]'
```

Ядро устанавливается как `pip install quite-admin` без ORM-зависимостей. Другие extras:
`sqlmodel`, `tortoise`, `peewee`, `gino-legacy`, `pydantic`, `fastapi`, `litestar`, `all`. GINO 1.x
требует отдельного окружения от современных SQLAlchemy-адаптеров. Установка из
распакованного архива исходников также остаётся доступной.

## Уязвимости зависимостей

`security.yml` запускает `pip-audit` и `npm audit` при пушах в `master`, PR, вручную и еженедельно.
Python проверяется со всеми зафиксированными extras/dev groups. npm показывает все
уровни и завершает job ошибкой при high/critical. Для публичных PR также работает
[GitHub Dependency Review](https://github.com/actions/dependency-review-action).
Ошибки сети/базы advisories не считаются чистым аудитом. Общих исключений advisory нет.
Приватные сообщения об уязвимостях и политика ранних версий описаны в `SECURITY.md`.

Зависимости документации закреплены через `package-lock.json` и overrides в
`package.json`. `scripts/diplodoc.cjs` обеспечивает совместимость CommonJS/ESM на Node 24.
Окружение проверяется строгой сборкой EN/RU и новым аудитом безопасности.

## Обязательные проверки и артефакты

`ci.yml` сначала выбирает проверки по Git diff, затем вызывает переиспользуемые workflows
Python, документации, JavaScript, браузеров, БД, совместимости и безопасности. Каждый
запуск проверяет метаданные релиза без установки зависимостей. План проверок виден
в сводке запуска.

| Изменённые файлы | Выбранные проверки |
| --- | --- |
| Документация, README, changelog или скрипты сборки документации | Строгая сборка EN/RU и демо |
| Python-код, примеры или скрипт экспорта демо | Python/lint/API, БД, совместимость, JavaScript, браузеры и docs/demo |
| Общие UI-шаблоны или статические ресурсы | Python, совместимость, JavaScript, браузеры и docs/demo |
| Исходники демо | JavaScript, браузеры и docs/demo |
| Python-тесты | Python, БД и совместимость; общие браузерные фикстуры также включают браузеры |
| Node-тесты / Playwright-сценарии или конфигурация | JavaScript / браузеры соответственно |
| `pyproject.toml` или `uv.lock` | Все потребители Python и аудит Python-зависимостей |
| `package.json` или `package-lock.json` | Документация, JavaScript, браузеры и npm audit |
| CI workflows, скрипты/тесты CI-защиты или неизвестные пути | Полный прогон |

Смешанные изменения объединяют нужные проверки. Для PR сравнивается head с общей базой
целевой ветки, для push — весь диапазон отправленных коммитов. Учитываются удаления
и оба пути переименованного файла. Если сравнение недоступно, например потеряна база
после force push, выполняются все проверки. Ручной запуск `ci.yml` всегда полный.
Еженедельный скан безопасности продолжает проверять обе экосистемы даже без обновления
зависимостей.

**CI ready** запускается всегда и требует успеха всех выбранных групп. Допустимы только
пропуски, явно указанные планом; ошибка выбора проверок, ошибка метаданных, отмена или
неожиданный пропуск блокируют gate. Сделайте **CI ready** обязательным check для `master`;
защита ветки настраивается в репозитории. **Release ready** успешен только после полного
прогона; для merge он должен оставаться необязательным. Пуш тега версии запускает только
публикацию и проверяет эти готовые результаты для точного SHA тега. Проверка версии
допускает Unreleased; тег требует даты в changelog.

CI проверяет Chromium, Firefox и WebKit на временной БД с вымышленными данными:
фильтры и поиск связанных ID, задержку поиска, выгрузку CSV/XLSX, inline-тоглы и
конфликты записи, календарь темы, узкую вёрстку и работу без JavaScript. При ошибках
сохраняются скриншоты и трассы. Python-матрица проверяет исходный checkout без сборки
дистрибутивов и проверки wheel/sdist. Артефакты документации отделены от assets релиза.

WebKit запускается на macOS. В Linux-сборке Playwright текстовые вложения сейчас
отображаются как страница вопреки корректному Content-Disposition
([ошибка upstream](https://github.com/microsoft/playwright/issues/43763)). На macOS
сценарий проверяет реальные скачивания CSV и XLSX без подмены заголовков ответа.

Pages публикуется после успеха workflow `release` и повторно проверяет полный CI для
SHA релиза. Обычный push, PR или ручной запуск CI сами по себе сайт не публикуют.
